# Firecrawl 多 Key 反向代理与管理面板

> 状态：Phase 1 规划完成，阻塞性开放问题为空，等待用户批准后进入实现。

## Goal

用 Go 编写一个可部署到服务器的 HTTP 反向代理，把多个 Firecrawl 免费账号的 API Key 聚合成**一个对外入口**。调用方只需持有代理签发的一个 API Key，像使用单个 Firecrawl Key 一样调用；代理负责轮询选 Key、感知额度耗尽/限流、自动故障转移，并通过 Web 面板管理上游 Key 与下游 API Key。

用户价值：把 N 个免费账号的 500 credits 汇成一个可用额度池，且切换过程对调用方完全透明——不用改客户端代码，不用手动换 Key。

## Background / 已确认事实

以下为查证 Firecrawl 官方文档后确认的事实，设计必须建立在这些之上。

### 上游 API 形态

- Base URL：`https://api.firecrawl.dev`，路径前缀 `/v1/...` 与 `/v2/...` 并存。
- 认证方式：`Authorization: Bearer fc-...`。代理只需替换这一个请求头。

### 错误语义（决定故障转移策略）

来源：Firecrawl API Reference — Errors

| 状态码 | 含义 | 可重试 | 代理应有的反应 |
|---|---|---|---|
| 401 | Key 缺失、格式错误或已吊销 | 否 | 该 Key 标记为**永久失效**，不再选中，面板告警 |
| 402 | 套餐额度耗尽或未配置计费 | 否 | 该 Key 标记为**额度耗尽**，不再选中，换下一个重试 |
| 403 | Key 权限不足 | 否 | 同 401，标记失效 |
| 429 | 超出每分钟速率限制**或**并发上限 | 是，需退避 | 该 Key 进入**临时冷却**，遵守响应的 `Retry-After` 头；换下一个重试 |
| 408 / 5xx | 上游超时或服务端故障 | 是 | 不是 Key 的问题，不应惩罚该 Key；按重试策略处理 |

关键区分：401/402/403 是 **Key 级别的终态**，429 是**临时状态**，408/5xx 是**上游问题**。三者的处理必须分开，否则会因为 Firecrawl 自身抖动把好 Key 全部误判为失效。

### 异步任务端点（必须 Key 粘连）

异步端点提交后返回 job id，后续轮询只有**提交它的那个 Key** 能查到：

- `POST /v2/crawl` → 返回 `{success, id, url}`
- `GET /v2/crawl/{id}`、`GET /v2/crawl/{id}/errors`、`DELETE /v2/crawl/{id}`
- `POST /v2/batch/scrape` → 返回 `{success, id, url, invalidURLs}`
- `GET /v2/batch/scrape/{id}`、`GET /v2/batch/scrape/{id}/errors`
- `/v1/` 下有对应的同名端点

若不做 job→Key 映射，轮询请求会被随机分发到其他 Key 并返回 404。

### 响应体内的绝对 URL（必须重写）

这是纯透明转发的第二个必然缺陷：

- `POST /v2/crawl` 与 `POST /v2/batch/scrape` 的响应含 `url` 字段，值是指向 `https://api.firecrawl.dev/...` 的状态轮询地址。
- `GET /v2/crawl/{id}` 的响应含 `next` 字段（分页游标），同样是指向 `api.firecrawl.dev` 的绝对 URL；当结果超过 10MB 或任务未完成时返回。

客户端 SDK 会**直接跟随**这些 URL。若不重写，客户端会绕过代理直连 Firecrawl，并带上代理签发的 Key → 401 失败。因此代理必须把响应体中的 `api.firecrawl.dev` 绝对 URL 改写为代理自身的对外地址。

### 额度查询端点（供面板展示用）

- `GET /team/credit-usage` → `{credits_total, credits_used, credits_remaining}`
- `GET /team/queue-status` → `{jobsInQueue, activeJobsInQueue, maxConcurrency, ...}`

注：调度**不依赖**这两个端点（已定为被动感知），但面板可用它们展示每个 Key 的余额，让用户直观看到额度池状况。

## Requirements

### R1 — 透明反向代理

- R1.1 转发范围由配置项 `PROXY_PATH_PREFIXES` 决定，默认覆盖 `/v1/` 与 `/v2/`。范围内的任意路径（含 Firecrawl 未来在这两个版本下新增的端点）原样转发到 `https://api.firecrawl.dev`，保留方法、路径、查询串、请求体与除认证外的请求头。Firecrawl 若发布新的版本前缀（如 `/v3/`），改配置即可支持，无需改代码。范围外的路径返回 404，不转发——这是为了避免与面板路由和静态资源冲突。
- R1.2 用选中的上游 Key 替换 `Authorization` 头。
- R1.3 上游响应的状态码与响应头原样返回。响应体默认**流式**透传，不整体读入内存；仅当该响应需要按 R1.4 重写、或需要从中提取 job id 时才缓冲，且缓冲有上限（超限则放弃重写、原样透传，不得截断）。
- R1.4 改写响应体中指向 `api.firecrawl.dev` 的绝对 URL 为代理对外地址（见 Background）。仅对 JSON 响应且仅针对已知字段（`url`、`next`）进行改写。对外地址由配置显式提供，不从请求 `Host` 头推断。
- R1.5 请求体需缓冲以支持故障转移时的重放，缓冲有上限（默认 8 MiB）。**超过上限的请求不缓冲，因而不支持故障转移**——单次转发，失败即原样返回上游响应。这是有意的取舍，需在 README 中写明。

### R2 — 被动额度感知与故障转移

- R2.1 不主动轮询上游额度接口来做调度决策。仅依据上游返回的状态码更新 Key 状态。
- R2.2 状态机：`可用` / `冷却中（至某时刻）` / `额度耗尽` / `已失效` / `手动禁用`。
- R2.3 收到 402 → 该 Key 置为「额度耗尽」；401/403 → 置为「已失效」；429 → 置为「冷却中」，冷却时长取 `Retry-After` 头，缺失时用默认退避。
- R2.4 遇到上述可转移错误时，自动换一个可用 Key 重试同一请求，直到成功或所有可用 Key 耗尽。重试次数上限可配置。
- R2.5 408/5xx 不改变 Key 状态。
- R2.6 所有 Key 都不可用时，返回一个语义明确的错误响应，让调用方能区分「代理没额度了」和「Firecrawl 挂了」。
- R2.7 冷却到期后 Key 自动恢复为可用，无需人工介入。

### R3 — Key 选择策略

- R3.1 在可用 Key 中轮询（round-robin），保证长期均匀消耗。
- R3.2 选择过程并发安全。

### R4 — 异步任务 Key 粘连

- R4.1 识别异步端点的提交响应，持久化 `job id → 上游 Key` 映射。
- R4.2 后续携带该 job id 的请求（状态查询、错误查询、取消）路由回原 Key，不参与轮询。
- R4.3 映射记录带过期清理，避免无限增长。

### R5 — 下游认证

- R5.1 调用方必须携带代理签发的 API Key（`Authorization: Bearer <proxy-key>`）。
- R5.2 代理 Key 在 Web 面板创建，创建时展示一次明文，之后仅存哈希。
- R5.3 支持创建多个代理 Key 并可单独吊销。
- R5.4 记录每个代理 Key 的调用量。
- R5.5 认证失败返回 401。

### R6 — Web 管理面板

形态：单页应用（Vue 3 + Vite + TypeScript + Tailwind），构建产物经 `go:embed` 打进二进制，最终仍只交付一个可执行文件。后端为面板提供一组 JSON API，与代理转发路径分离。

- R6.1 **总览页**：额度池汇总（所有可用 Key 的剩余 credits 之和 / 总额）、各上游 Key 的状态卡片、按固定间隔自动刷新并显示上次刷新时间。
- R6.2 **上游 Key 管理页**：录入新 Key（粘贴 + 备注命名）、启用/禁用、删除；列表展示脱敏后的 Key、当前状态、冷却剩余秒数、剩余额度、累计调用数。
- R6.3 **API Key 管理页**：创建下游代理 Key（取名）、列表展示名称/前缀/调用数/创建时间、吊销。创建时以弹窗展示一次完整明文并提供复制。
- R6.4 面板需登录保护：单一管理员密码，登录后签发 session cookie（HttpOnly）。无多用户与角色体系。
- R6.5 支持暗色主题；操作结果以 Toast 反馈。
- R6.6 面板 API 与代理转发路径必须使用不同的认证机制：面板走 session cookie，代理走 `Authorization: Bearer`。代理 Key 不得用于访问面板 API，反之亦然。

### R7 — 持久化

- R7.1 使用本地 SQLite 存储：上游 Key 及其状态、下游代理 Key、job→Key 映射、用量计数。
- R7.2 重启后状态保留：已耗尽/已失效的 Key 不会被重新当作可用而再撞一次；未过期的 job 映射仍能正确路由。
- R7.3 上游 Key 明文不得出现在日志中；面板与 API 返回时一律脱敏（如 `fc-****abcd`）。

### R8 — 可运维性与交付

- R8.1 单一配置来源（监听地址、SQLite 路径、上游 base URL、对外地址、管理员密码、重试上限、默认冷却时长等），环境变量优先，便于容器化注入。
- R8.2 结构化日志：每次请求记录选中的 Key（脱敏）、上游状态码、是否发生转移、耗时。
- R8.3 提供 `/healthz` 健康检查端点，不需要认证。
- R8.4 交付物：Dockerfile（多阶段构建，前端构建 → Go 构建 → 精简运行镜像）与 `docker-compose.yml`，SQLite 数据目录以卷挂载。
- R8.5 代理自身只监听 HTTP，TLS 与域名由前置网关（Nginx/Caddy）处理，compose 中给出一个可选的 Caddy 服务示例。程序内不处理证书。
- R8.6 容器以非 root 用户运行，数据卷权限在镜像内预置。

## Acceptance Criteria

- [ ] AC1：配置 3 个上游 Key，把其中一个改成会返回 402 的无效 Key，`POST /v2/scrape` 仍能成功返回，且该 Key 被标记为「额度耗尽」。
- [ ] AC2：上游返回 429 且带 `Retry-After: 30`，该 Key 状态变为冷却中且剩余时间约 30 秒，请求由另一个 Key 完成。
- [ ] AC3：上游返回 500 时，Key 状态保持「可用」，不被误判。
- [ ] AC4：`POST /v2/crawl` 提交后，连续多次 `GET /v2/crawl/{id}` 全部命中同一个上游 Key，返回真实状态而非 404。
- [ ] AC5：`POST /v2/crawl` 响应中的 `url` 字段与 `GET /v2/crawl/{id}` 响应中的 `next` 字段均指向代理地址，不含 `api.firecrawl.dev`。
- [ ] AC6：所有 Key 均不可用时，返回可区分的错误响应（非裸 502）。
- [ ] AC7：不带代理 Key 或带已吊销的代理 Key 调用，返回 401。
- [ ] AC8：面板可新增一个上游 Key，无需重启，下一次请求即可能选中它。
- [ ] AC9：面板创建的代理 Key 明文仅在创建时展示一次；数据库中不存明文。
- [ ] AC10：重启服务后，此前被标记为「额度耗尽」的 Key 仍为耗尽状态；未过期的 job 映射仍能正确路由。
- [ ] AC11：日志与面板接口的任何输出中都不出现上游 Key 明文。
- [ ] AC12：`docker compose up -d` 后服务可用，面板可访问；`docker compose down` 再 `up` 后数据（上游 Key、代理 Key、Key 状态）完整保留。
- [ ] AC13：面板 session cookie 不能用于调用 `/v1/*`、`/v2/*` 代理路径；代理 API Key 不能用于访问面板 API。两套认证互不通用。
- [ ] AC14：`/healthz` 无需认证即可返回 200。
- [ ] AC15：请求体超过缓冲上限时仍能成功转发（单次、不重试）；未超限时故障转移正常工作。

## Out of Scope

- 主动轮询上游额度做调度决策（已明确采用被动感知）。
- 上游返回内容的缓存、去重或改写（除 R1.4 的 URL 重写外）。
- 自动注册 Firecrawl 免费账号。
- 多租户、计费、配额分配。
- 面板的用户体系（多用户、角色、权限）——单管理员即可。
- 自建 Firecrawl 实例的适配。
- 程序内处理 TLS 证书（交由前置网关）。
- 请求日志检索、用量图表、告警阈值（面板范围已定为不含这些）。

## 已知限制

这些不是缺陷，是设计取舍的结果，需在 README 中对使用者写明：

- **请求体超过 8 MiB 时不支持故障转移**（R1.5）。为避免把大请求的内存占用变成攻击面。Firecrawl 的请求体是 JSON 选项，实践中远小于此。
- **不支持多副本部署**。Key 状态与轮询游标在进程内存中，多副本各自维护一份会导致同一个 Key 被并发超用、429 冷却状态不共享。扩容需要把 Key 池状态外置，属于另一次项目级改造，不是配置调整。
- **面板展示的额度可能滞后**。后台刷新间隔默认 10 分钟。调度不依赖它，因此不影响正确性。
- **调用计数可能在崩溃时丢失最后几秒**。换取消除每请求一次的 DB 写入开销。Key 与配置这类关键数据是同步写的，不会丢。

## Key Decisions

| 决策 | 选择 | 理由 |
|---|---|---|
| 额度感知方式 | 被动感知（依状态码） | 零额外请求；主动查询依赖上游接口稳定性，收益不抵复杂度 |
| 端点覆盖 | 全端点透明转发 | 新端点自动支持，无需跟着 Firecrawl 升级 |
| 异步任务路由 | job→Key 映射表并落盘 | 广播探测会把每次轮询放大成 N 次请求，成本不可接受 |
| 状态持久化 | SQLite | 服务器部署会重启；重启即重置会反复浪费请求撞已耗尽的 Key |
| 下游认证 | 面板签发的多个代理 API Key | 可分别统计与吊销 |
| 面板形态 | Vue 3 + Vite + TS + Tailwind 的 SPA，构建产物 `go:embed` 进二进制 | 界面质感与实时刷新体验更好；embed 保证运行时仍是单进程 |
| 面板认证 | 单管理员密码 + HttpOnly session cookie | 无多用户需求；与代理 Key 认证彻底隔离 |
| 部署交付 | Docker 镜像 + docker-compose，TLS 交前置网关 | 部署与升级一条命令；证书运维交给成熟网关而非自研 |
| SQLite 驱动 | 纯 Go 实现（`modernc.org/sqlite`），不启用 CGO | 免 CGO 交叉编译，可用精简基础镜像，构建链更简单 |
